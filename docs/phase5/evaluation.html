Concept

What is a benchmark

Validation loss (everything Phases 1-3 optimized for) measures one thing: how surprised the model is by the next real token in held-out text. It never asks whether the model can actually reason, recall a fact, or solve a problem — a model can have great loss and still fail completely at tasks that require using what it learned.

A benchmark is a fixed set of questions with known correct answers, designed to test a specific capability directly — commonsense reasoning (HellaSwag, PIQA), grade-school math (GSM8K), or code generation (HumanEval). Instead of "how surprised was the model," it asks "did the model get the right answer."

Analogy: A student who's read every textbook cover to cover (low "surprise" at anything in the books) isn't the same as a student who can pass the actual exam. Validation loss is the reading; benchmarks are the exam.
Concept

The random-chance floor

Most of these benchmarks are multiple-choice — pick the correct continuation from 4 options. That means guessing randomly, with zero understanding, already scores ~25%. A model has to clear that floor by a meaningful margin before a score means anything at all.

This is the honest expectation, not a hedge

This project's largest model (150M params, 2B tokens at most) is trained on a tiny fraction of the compute that models like GPT-2-124M or SmolLM-135M saw. Scoring near the random-chance floor on several benchmarks is a realistic, likely outcome — not evidence something's broken. Deciding that's an acceptable, reportable result before running anything is exactly the kind of honesty this project has stuck to throughout (see Phase 2's tokenizer regression, Phase 3's surprising Run 3, Phase 4's tokenizer-mismatch finding).

Concept

Error analysis

A single benchmark score (say, "34% on PIQA") hides everything interesting. Error analysis means actually reading the model's worst-scoring examples and asking why it got each one wrong — is it a tokenization artifact (the 32K BPE tokenizer splitting a key word oddly), a genuine reasoning gap, or just a question requiring knowledge the model never saw enough of in training to encode.

Analogy: A teacher who only sees "62% on the exam" learns nothing about how to help the student. A teacher who reads the specific wrong answers sees the pattern — maybe every missed question involves fractions, or every one is a word problem with extra irrelevant numbers. The score is a symptom; reading the actual mistakes is the diagnosis.
Concept

The feedback loop

Once you know what kind of question the model fails, the natural next step is generating more training examples that specifically target that weakness — math questions with step-by-step solutions if math was the gap, "explain your reasoning" style data if commonsense was the gap — then fine-tuning on that targeted data and re-running the benchmarks to see if the gap actually closed.

1

Benchmark

Run the eval suite, get real scores per category.

2

Diagnose

Read the actual wrong answers, categorize the failure modes.

3

Generate targeted data

Use a teacher model to produce examples aimed at the specific gap found.

4

Retrain, re-benchmark

Fine-tune on the targeted data, run the same benchmarks again, see if the gap closed. Repeat.

This is RLHF's feedback loop, without the "RL"

Production RLHF pipelines run a version of exactly this loop — find weaknesses, generate targeted data (often from human feedback or a reward model instead of a teacher LLM), retrain, repeat. Doing it manually here, with a teacher model standing in for the feedback signal, is the same shape of process at a scale you can actually see and understand end to end.

The harness problem

lm-evaluation-harness expects a HuggingFace-style model (an AutoModelForCausalLM-shaped interface). This project's GPT class and custom BPE tokenizer aren't that — a small adapter implementing the harness's LM interface (mainly loglikelihood, which is all most multiple-choice benchmarks actually need) is required first. Infrastructure, not a re-architecture — see sprint-plan.md.

Q&A

Questions

Phase 3 already compared models by validation loss. Isn't that enough to know which one is "better"?

Loss tells you how well a model predicts held-out text from the same distribution it trained on — it says nothing about whether the model can use that knowledge to answer a question, solve a problem, or reason through steps it wasn't directly shown. Two models can have near-identical loss and score very differently on an actual task, especially at this scale, where small differences in what got memorized vs. generalized can matter more than the aggregate loss number suggests.

Given what Phase 4 found about the teacher's cost, is running the full feedback loop (Task 5.3-5.4) even worth it?

Genuinely uncertain, same as Phase 4 — and worth deciding with real data in hand rather than in advance. The feedback loop's precondition is a model with partial competence and a few isolated weak spots to target. If Step 2's benchmarks come back near the random-chance floor across the board (a real possibility given this project's scale), that's a sign the model doesn't have isolated gaps to patch — it has a general scale limitation, which targeted synthetic data can't fix regardless of how much teacher time you spend generating it.

So the honest plan is: benchmark first, look at the actual failure patterns, and only then decide whether a small, scoped round of targeted data is worth the same kind of teacher-generation cost Phase 4 weighed — not commit to the full multi-round loop from docs/plan.md before knowing whether the precondition for it to work is even met.

What if every model just scores at random chance on every benchmark?

That would still be a real, reportable result — and consistent with this project's own established pattern of treating an honest negative finding as valuable, not as something to bury (Phase 2's tokenizer regression, Phase 4's tokenizer-mismatch blocker). "Here's the compute/data threshold below which standard benchmarks show no signal, measured directly rather than assumed" is a genuinely useful thing to know and document, and arguably a more interesting portfolio finding than a clean win would be — it's exactly the kind of scale intuition Phase 3's Chinchilla analysis was already building toward.
