Overview

The one-sentence version

A language model is a machine that looks at a sequence of words and guesses what comes next. That's all it does. Training is just doing this billions of times, being wrong, and slowly getting less wrong.

Each section below covers one of these steps in detail.

Step 1

Words become numbers (Tokenization)

Computers don't understand text. So the first step is converting every word (or word-piece) into a number called a token ID. This mapping is fixed: it's the vocabulary, like a dictionary with ~50,000 entries.

The464
cat3797
sat3332
on319
the262
mat2603

The model only ever sees these numbers. The vocabulary maps number ↔ word so you can convert back at the end.

Step 2

Numbers become vectors (Embeddings)

Token ID 3797 ("cat") is just a number with no meaning. So each ID is looked up in a giant table that converts it into a vector: a list of ~768 numbers that the model learns meaning into over training.

Think of a vector as a point in 768-dimensional space. After training, words with similar meanings end up close together in that space.

cat
→
[0.21, -0.84, 0.13, 0.67, -0.02, ... × 768]
dog
→
[0.19, -0.81, 0.11, 0.65, -0.01, ... × 768]
car
→
[-0.55, 0.32, 0.74, -0.12, 0.88, ... × 768]

"cat" and "dog" vectors are similar (both animals). "car" is very different. The model learns this on its own. Nobody labels it.

Step 3

Tokens look at each other (Attention)
∑
Scaled dot-product attention
Attention(Q, K, V) = softmax(QKT / √dk) · V
Q = query, K = key, V = value (all linear projections of the input).
dk = head dimension (e.g. 64). Dividing stabilises gradients for large dk.
Softmax converts raw scores into weights that sum to 1.
Causal mask sets future positions to −∞ before softmax so they become 0.

Now the model has a sequence of vectors, one per token. Each token is still isolated at this point. "sat" doesn't know it's the cat that's sitting. Attention fixes this.

For every token, attention asks: "which other tokens are most relevant to understanding me right now?" It then mixes in information from those tokens proportionally.

Example: "The bank by the river was flooded". "bank" needs to figure out it means riverbank, not a financial bank. Attention lets it look at "river" and "flooded" and weight them heavily.

After attention, each token's vector is a blend of the whole context, weighted by relevance. "bank" now has "river" and "flooded" baked into it.

Multi-head attention means this happens 12 times in parallel with different "questions" each time. One head might track grammar, another entities, another positional relationships.

Variant

Flash Attention

Flash Attention computes the exact same result as standard attention. The difference is purely about how it runs on a GPU.

Standard attention writes the full Q×K score matrix to GPU memory (VRAM) before computing the softmax. For a 1024-token sequence with 12 heads, this matrix gets large fast, and shuttling data back and forth to VRAM is slow. That memory bottleneck, not the computation itself, is what limits speed.

Standard attention

Computes all Q×K scores at once, writes the full matrix to VRAM, reads it back for softmax, then multiplies by V.

Memory usage scales with sequence length squared: 1024 tokens → 1M cells per head.

Memory bottleneck

Flash Attention

Tiles the computation into small blocks that fit in the GPU's fast on-chip cache (SRAM). Never writes the big matrix to VRAM.

Same output numbers. 2–4× faster. Uses far less memory and enables much longer sequences.

2–4× faster

In nanoGPT, you get Flash Attention for free on PyTorch 2.0+. The code calls F.scaled_dot_product_attention(..., is_causal=True) and PyTorch uses the optimized kernel automatically. If that function is unavailable, it falls back to the slow manual version with the same numerical output, just slower.

Step 3.5

Each token thinks for itself (MLP)

After attention has mixed information between tokens, each token's vector is passed through a small feedforward network called the MLP (Multi-Layer Perceptron). This happens independently for every token — no communication between positions here.

The structure is two linear layers with a nonlinearity in between:

Token vector (768 dimensions)
↓
Linear layer: expand to 3072 dimensions (4×)
↓
GELU nonlinearity
↓
Linear layer: compress back to 768 dimensions
↓
Token vector out (768 dimensions)

The expansion to 4× gives the network room to compute functions that a single linear layer could not. A linear layer by itself can only learn straight-line relationships. The GELU nonlinearity breaks that constraint, letting the MLP approximate much more complex transformations.

Split of responsibility between attention and MLP

Attention

Moves information between tokens. Decides what context each token should gather from the rest of the sequence. Operates across positions.

MLP

Processes information within each token. Takes the context-enriched vector from attention and computes what it means. Operates per position independently.

Mechanistic interpretability research (primarily from Anthropic) suggests the MLP layers are where most factual knowledge is stored. If you ablate specific MLP neurons you can selectively remove specific facts from the model's output — things like "the capital of France is Paris" appear to live in particular MLP weights rather than in the attention patterns. Attention handles structure and routing; MLP handles knowledge retrieval and computation.

Why GELU specifically

ReLU was the standard nonlinearity for years: it outputs 0 for negative inputs and the input itself for positive inputs. GELU (Gaussian Error Linear Unit) is a smoother version that doesn't hard-clip to zero — it tapers off gradually for negative values. Empirically GELU trains better for language models, which is why GPT-2 and most transformers since have used it. The difference in practice is small but consistent enough that GELU became the default.

Step 4

This repeats 12 times (Transformer Blocks)

One pass of attention + a small feedforward network is called a block. The model stacks 12 of these blocks on top of each other. Each reads the output of the previous one.

Early blocks catch simple patterns. Later blocks catch abstract reasoning.

Block 1: spelling, common phrases
↓
Block 2–6: grammar, syntax, entities
↓
Block 7–12: meaning, facts, reasoning
↓
Output: predict next token
Step 5

How wrong was the guess? (Loss)
∑
Cross-entropy loss
L = −log(pcorrect)
pcorrect = the probability the model gave to the actual next token.
If the model said "mat" has 4% probability → L = −log(0.04) ≈ 3.22.
If the model said "mat" has 72% probability → L = −log(0.72) ≈ 0.33.
In practice averaged over all tokens in the batch.

After the model produces scores for all 50,000 possible next tokens, we compare against the actual next token. The resulting score is called loss. High loss means a bad prediction, low loss means a good one.

The function used is cross-entropy: it punishes you more the lower the probability you gave to the correct answer.

Step 6

Figure out who's to blame (Backpropagation)
∑
Chain rule (the engine of backprop)
∂L/∂w = ∂L/∂y · ∂y/∂w
∂L/∂w = how much does loss change if we nudge weight w?
Computed by multiplying gradients backwards layer by layer.
PyTorch builds a computation graph during the forward pass and traverses it in reverse with loss.backward().
You never write this. It's automatic.

The model has millions of weights, which are the numbers inside all those matrix multiplications. When it makes a bad prediction, which weights caused the error?

Backpropagation answers this using the chain rule from calculus. Starting from the loss, it works backwards through every operation and computes a gradient for each weight: if you increase this weight slightly, does the loss go up or down?

You don't write this. PyTorch does it automatically with loss.backward().

Step 7

Fix the weights (Gradient Descent + AdamW)
∑
Basic gradient descent
w ← w − η · ∂L/∂w
η (eta) = learning rate, controls step size.
w = weight. ∂L/∂w = gradient from backprop.

AdamW update (simplified)
m ← β₁m + (1−β₁)·g    // momentum
v ← β₂v + (1−β₂)·g²   // variance
w ← w − η · m̂/(√v̂ + ε)
g = gradient. β₁ ≈ 0.9, β₂ ≈ 0.999 (nanoGPT defaults).
m = running mean of gradients (momentum). v = running variance.
Dividing by √v̂ makes steps smaller for weights that fluctuate wildly.

What a gradient actually is

A gradient is a rate of change, which is just a slope. If you nudge a weight by a tiny amount and the loss changes a lot, that weight has a steep gradient. If the loss barely moves, the gradient is nearly flat.

But the model has millions of weights. So instead of a single slope, you get a gradient for every weight, computed simultaneously by backpropagation. Each one answers the same question: "for this specific weight, does a small increase make the loss go up or down, and by how much?"

Think of it this way. Imagine loss as a surface plotted against just two weights:

loss surface (two weights, simplified)
high │████▓▒░ · ░▒▓
│██▓▒░ · · ░▒
loss │▓▒░ · · ·  ★  · ░
│▒░ · · · ·  · · ░
low │░ · · · · · · · ░
└─────────────────────── weight value
★ = minimum (what training is trying to find)

Every point on that surface is a combination of weight values with a corresponding loss. The gradient at your current position tells you which direction is uphill for each weight. You move in the opposite direction to go downhill, toward lower loss.

In reality, there are millions of weights, not two. You can't visualize it, but the math works the same way: each weight has its own slope at the current position, and you step each one downhill simultaneously.

The learning rate problem

The gradient tells you the direction, not how far to step. That's the learning rate (η). If you step too far, you overshoot the minimum and bounce around. Too small and you'll converge, but it'll take 10× as long.

Too large

Steps overshoot the minimum. Loss bounces up and down instead of converging. Training becomes unstable or diverges entirely.

Just right

Loss decreases steadily each step. The model converges to a good minimum in a reasonable number of steps.

Too small

Steps are so tiny that training takes 10× longer than needed. Also risks getting stuck in shallow local minima.

nanoGPT doesn't use a fixed learning rate. It uses a cosine schedule: start at the peak rate, decay it slowly following a cosine curve down to near zero by the end of training. This gets the fast early progress of a high rate and the precise final convergence of a low rate.

Why plain gradient descent isn't enough

Basic gradient descent uses the gradient from the current batch only. That gradient is noisy: one batch of 512 tokens isn't a perfect representation of the whole dataset, so the gradient direction is slightly wrong every step. You end up taking many jagged steps instead of going straight to the minimum.

nanoGPT uses AdamW, which fixes two things:

Momentum

Keeps a running average of recent gradients. If the gradient has pointed in the same direction for many steps, that direction gets more weight. Single noisy steps don't throw it off course.

Per-weight learning rate

Tracks how much each weight has been updated recently. Weights that change constantly get a smaller step. Weights that rarely update get a bigger one. Each weight effectively self-tunes its own step size.

Plain gradient descent vs AdamW, framed as an algorithms problem

Plain gradient descent works correctly but wastes steps, for the same reason random sort does. It gets to the answer eventually, but ignores information that was always available and could make it faster.

Random sort / plain GD

Picks elements without using information about the data. Each step is computed in isolation, throwing away everything learned from previous steps. Correct, but inefficient.

Quicksort / AdamW

Exploits structure that was always there. AdamW uses the history of gradient directions (momentum) and the history of per-weight volatility (adaptive rate). Same information, used instead of discarded.

The analogy breaks down in one place: quicksort is provably optimal for comparison sorts, but AdamW is not the final word on optimizers. Newer ones like Adafactor, SOAP, and Muon improve on it in various ways. The optimizer space is still active research in a way that sorting algorithms mostly are not.

Detail

AdamW internals

AdamW is built on top of Adam, which itself is built on top of plain gradient descent. Each layer adds one mechanism that fixes a specific problem with the layer below it.

Layer 1: plain gradient descent

Take the gradient, multiply by the learning rate, subtract from the weight. Simple, but the gradient is noisy (it's computed from one small batch) and every weight uses the same step size regardless of how different their gradients are.

Layer 2: momentum (the first moment)

Instead of using the raw gradient directly, keep a running exponential average of all past gradients. Call this m (the first moment).

The effect: if the gradient has been pointing in roughly the same direction for many steps, m builds up in that direction. One noisy batch pointing the wrong way barely moves it. This smooths out the jagged path that plain gradient descent takes.

The decay factor β₁ (typically 0.9) controls how much history to remember. β₁ = 0.9 means each step, the old average counts for 90% and the new gradient counts for 10%.

Layer 3: adaptive learning rate (the second moment)

Keep a second running average, this time of the squared gradient. Call this v (the second moment, also called the variance estimate).

A weight that consistently has large gradients will have a large v. Dividing the step by √v shrinks that weight's effective learning rate automatically. A weight that rarely updates has a small v, so its effective learning rate stays larger.

This is what "adaptive" means in Adam: each of the model's millions of weights ends up with a different effective step size, tuned automatically based on its own gradient history. You set one global learning rate and the optimizer distributes it sensibly.

The W in AdamW: decoupled weight decay

Weight decay is a regularization technique that shrinks all weights slightly toward zero every step, which prevents them from growing arbitrarily large and overfitting. In the original Adam, weight decay was implemented by adding it to the gradient before the update. This created a bug: the adaptive learning rate then scaled the weight decay differently for each weight, meaning weights that updated rarely got much less regularization than weights that updated often. The regularization was uneven.

AdamW fixes this by applying weight decay directly to the weights, completely separately from the gradient update step. The decay is now uniform across all weights regardless of their gradient history. This is the only difference between Adam and AdamW, but it consistently improves generalization in practice, which is why AdamW replaced Adam as the default for language models.

Is AdamW still the best?

For most LLM training runs it's still the default. LLaMA, Mistral, and most public models use it. But it has real challengers:

Muon (2024)

Uses Nesterov momentum with an orthogonalization step that makes gradient updates more geometrically uniform. Several recent training runs have shown better loss per compute than AdamW. Gaining traction in research.

Adafactor

Memory-efficient variant. Instead of storing a full second-moment matrix, it factorizes it into row and column statistics. Used by Google for T5 and some Gemini variants where memory is the constraint, not compute.

SOAP

Shampoo with Adam in Projection Space. Uses approximate second-order curvature information (Kronecker-factored preconditioning). Better convergence per step, but more expensive to compute. Not yet mainstream.

Sophia

Uses diagonal Hessian estimates (second-order information) to scale updates. More theoretically principled than Adam's variance estimate, but the Hessian computation adds overhead that makes it hard to justify in practice.

AdamW is the safe default for most training runs. Muon is worth watching, but the tooling and practical guidance around it is still maturing. The optimizer you pick matters far less than data quality, model architecture, and learning rate schedule.

Putting it together

The training loop

Everything above repeats in a loop, hundreds of thousands of times, across millions of text examples.

1

Grab a batch of text

Pull ~512 tokens of text. Input = tokens 1–511. Target = tokens 2–512 (shifted by one). The model predicts each next token.

Input: "The cat sat on the" → Target: "cat sat on the mat"
2

Forward pass

Run input through all 12 transformer blocks. Each token produces a probability distribution over 50,000 tokens.

Model gives "mat" a 4% probability. It should be near 100%.
3

Compute loss

Cross-entropy compares predictions vs. correct next tokens. One number: how wrong was this batch?

Loss = 3.22 early → 0.33 after training
4

Backward pass

PyTorch computes gradients for every weight automatically. Each weight now knows which direction reduces its error.

"Weight #4,291,032 contributed 0.003 to the error. Nudge it down."
5

Update weights + repeat

AdamW nudges every weight slightly. Zero gradients. Grab next batch. Repeat 100,000+ times.

When loss stops falling, training is done. The weights ARE the model.

Q & A

What is a Transformer?

The word "Transformer" refers to the overall architecture — the specific arrangement of components that makes modern language models work. It was introduced in the 2017 paper "Attention Is All You Need" and has been the dominant architecture for language models ever since.

The name comes from the fact that it transforms a sequence of tokens into a new sequence of context-aware representations — each token starts as an isolated vector and ends as a vector that has absorbed information from the entire context around it.

The three parts

A transformer is made of three layers stacked in order:

raw text
"The cat sat on the mat"
↓ tokenizer
token IDs
[464, 3797, 3332, 319, 262, 2603]
↓ embedding lookup
1. Embedding layer
Token Embedding + Position Embedding
Each token ID → a vector of 768 numbers
Position 0,1,2... → another vector of 768 numbers
Add them together → input to the blocks
↓ repeated N times (e.g. 12)
2. Transformer blocks
Block (× n_layer)
LayerNorm → CausalSelfAttention → residual add
LayerNorm → MLP → residual add
↓
3. Output head
LayerNorm + Linear (lm_head)
768 values per token → 50,257 scores
One score per word in the vocabulary
Highest score = predicted next token
↓
output
logits [vocab_size] → next token prediction

Why this arrangement works

Before Transformers, sequence models (RNNs, LSTMs) processed tokens one at a time left-to-right. Token 500 could only see token 499 through a compressed "hidden state" — information from early tokens faded. Transformers process all tokens simultaneously and let every token look directly at every other token via attention. No fading, no bottleneck.

The repeated block structure means each block refines the representations slightly. Block 1 might learn basic grammar patterns, block 6 might learn entity relationships, block 12 might learn high-level reasoning. Stacking more blocks = more capacity, at the cost of more compute and memory.

What makes it a language model

The architecture above is just a transformer. It becomes a language model by training it to predict the next token — given "The cat sat on the", predict "mat". Do this across billions of examples and the weights learn to encode grammar, facts, reasoning, and style. The architecture does not change — only the training objective and the data.

Q & A

What happens with a new word or name?

Unfamiliar words get split into pieces. This is called Byte Pair Encoding (BPE). The tokenizer was trained on a huge corpus and learned which letter-chunks appear together most often. Those chunks become vocabulary entries.

A name like "Reddy" that wasn't common enough to get its own token gets split into the closest pieces the vocabulary knows:

Reddy
→
RedRed
dydy

The split depends on the vocabulary. It could also be R + eddy or Re + ddy. The tokenizer picks whatever uses the fewest tokens. Each piece gets its own embedding vector, and through attention the model recombines them to understand the full word in context.

Common word

Gets its own token.

"cat" → token #3797. One embedding.

Rare name

Split into subwords.

"Schwarzenegger" → ["Schwar","zen","egg","er"]. 4 tokens.

Truly unknown

Falls back to characters or bytes.

"🎯" → bytes of the emoji. Never fully unknown.

Practical Concepts

RAG and embeddings

Embeddings are not standardized across models. But RAG sidesteps this entirely. Here's how.

First, there are two completely different things called "embeddings" that get mixed up:

Internal token embeddings

768-number vectors inside the model. Private to that model. Used during the forward pass. Never leave the model. Completely incompatible across models.

Retrieval embeddings (RAG)

Vectors from a separate embedding model (like sentence-transformers). Used to search a document database. Totally separate from the LLM.

How RAG actually works

1

Embed your documents (done once)

Run every chunk through a dedicated embedding model. Each chunk becomes a vector stored in a vector database.

"The Eiffel Tower is 330m tall." → [0.12, -0.44, 0.87, ...]
2

Embed the user query (same model)

Run the query through the exact same embedding model. Now query and documents are in the same vector space.

"How tall is the Eiffel Tower?" → [0.11, -0.41, 0.85, ...]
3

Find the closest documents

Measure cosine similarity between query vector and all document vectors. Grab the top 3–5 closest.

Query ↔ Eiffel Tower chunk = 0.94 similarity ✓
4

Pass as plain text to the LLM

Retrieved chunks convert back to text and paste into the prompt. The LLM reads them as normal tokens. No embedding magic needed.

Prompt: "Context: [chunk]. Question: How tall? Answer:"
5

LLM generates the answer

The LLM (any model) reads the context text and answers. It never touched the retrieval embeddings. The two models are fully decoupled.

Output: "The Eiffel Tower is 330 metres tall."

The one hard rule

Use the same embedding model for both building the document database and encoding queries. If you mix models, the vectors are in different coordinate systems and similarity scores become meaningless. The generation LLM can be anything.

Q & A

Why not standardize embeddings to cut overhead?

Good instinct. But the overhead is much smaller than it looks, and standardizing the space turns out to be fundamentally hard.

The overhead is actually tiny

The embedding model in RAG is typically 22M–110M parameters. The LLM is 7B–70B+. Time breakdown of a real RAG call:

Embed the query
~10ms
Vector DB search
~20ms
LLM generation
~2000ms

The embedding step is under 2% of total latency. The LLM generating tokens one-by-one is the real bottleneck.

Why standardization is fundamentally hard

The embedding space isn't a format you can agree on. It emerges from training, and two models trained differently end up with completely different coordinate systems even at identical dimensions.

Dimensions vary

Models use 384, 768, 1024, 1536, 3072 dims. You can't compare different-shaped vectors, and there's no obviously correct standard size.

Progress would freeze

Agreeing on a standard today means a better model tomorrow breaks every vector database in the world. Standardizing locks in the current best.

Tasks need different spaces

Code embeddings cluster by functionality. Medical by symptom. Legal by jurisdiction. One space can't be optimal for everything.

The space isn't designed

You can standardize a file format because a human defined it. Embedding spaces emerge from training data, so you can't agree on one without training everyone identically.

What people actually do instead

DE FACTO

Converge on popular APIs

OpenAI's text-embedding-3-small and Cohere's embed-v3 have become informal standards through sheer adoption. Not official, but interoperable in practice.

MRL

Matryoshka embeddings

A training technique where a 1536-dim vector can be safely truncated to 768, 384, or 256 dims without losing much quality. Trade speed for accuracy at query time.

CACHE

Cache query embeddings

If users ask similar questions repeatedly, cache the embedding vector. The 10ms overhead disappears for repeated queries.

ANN

Approximate nearest neighbour search

Vector databases (FAISS, Pinecone, Weaviate) use index structures that find closest vectors in milliseconds across millions of documents without checking every one.

The real latency bottleneck in RAG is the LLM reading a long context and generating tokens autoregressively, not the embedding step. Techniques like speculative decoding and KV caching target that, not the embedding model.

Practical Concepts

Training cost and VRAM

Not exponential, but it does compound in ways that feel that way. The costs come from a few different scaling relationships stacked on top of each other.

The FLOP accounting

The standard estimate is that training a model costs roughly 6 × N × D floating point operations, where N is parameter count and D is number of training tokens. So cost scales linearly with parameters and linearly with data. Double the model, double the cost. Double the data, double the cost.

The compounding comes from the Chinchilla result: to train a model optimally, you need roughly 20 tokens per parameter. So if you want to double your parameter count and keep training optimal, you also need to double your data. That makes cost scale roughly as N², which is quadratic, not exponential. Still painful, but not runaway.

Linear in parameters

Each token touches every parameter once in the forward pass. 2× the parameters = 2× the compute per token.

Linear in data

Each training token costs the same to process. 2× the tokens = 2× the total training cost.

Quadratic in sequence length

The attention Q×K matrix grows as T². A 2048-token context costs 4× the attention compute of a 1024-token context. This is why Flash Attention matters.

Where it feels exponential

Two things make the costs feel worse than the math suggests.

First, capability doesn't scale linearly with compute. You might need 10× the compute to get a model that scores 2× better on a benchmark. The returns are diminishing, so you end up spending exponentially more to get linear capability gains.

Second, infrastructure costs are non-linear. At small scale you rent cloud GPUs. At medium scale you need dedicated clusters with high-speed interconnects. At large scale you're building your own datacenters. Each tier is a step change in cost per FLOP, not a smooth curve.

GPT-3's 10-year single-H100 figure is why it took OpenAI roughly 10,000 A100s for about a month — costing an estimated $5–12M in cloud compute at the time. No single GPU can hold a 175B model in VRAM anyway, which brings us to the next table.

Training VRAM and inference VRAM are different problems. To just load a model and run it, you need roughly 2 bytes per parameter in BF16, or 0.5 bytes per parameter in 4-bit quantization. Training needs significantly more on top of that for gradients and optimizer states.

Training VRAM is a different calculation

During training you also need: gradients (~2 bytes/param), Adam optimizer states (~8 bytes/param for first + second moment in FP32), and activations (varies with batch size). Total comes to roughly 16–20 bytes per parameter for a full training run. Your 75M model needs roughly 1.2–1.5GB for training — trivial. A 27B model needs ~430–540GB for full training, which is why almost nobody trains 27B+ models from scratch without model parallelism across many GPUs.

Small model on a consumer GPU

At 75M to 300M parameters on a single consumer GPU (e.g. RTX 4090 or 5070 Ti), costs scale predictably. A 4× bigger model costs roughly 4× more to train, and you need 4× the data to keep training optimal. The quadratic attention cost only becomes a real problem at long context lengths.

Practical Concepts

Context size and the KV cache

Context size is how many tokens the model can see at once. There are three separate things that determine and constrain it, and most explanations mix them up.

1. The training context limit

During training, every batch has a fixed sequence length. The model learns positional embeddings only up to that length. If a model was trained with a max sequence length of 8192 tokens, it has never seen position index 8193 during training — its positional encoding for that slot is undefined, in the same way a lookup table has no entry for a key that was never inserted.

Modern models use RoPE (Rotary Position Embedding) rather than learned absolute positions. RoPE encodes position as a rotation in the embedding space, which means it can mathematically extrapolate beyond its training length — the formula still produces a number. The problem is the model was not trained to handle those rotation angles, so output quality degrades past the training limit. How much it degrades depends on the model and how far you push it.

2. The KV cache: why context takes VRAM

This is the part beginners consistently miss. During inference, the model generates tokens one at a time. To generate token N, it needs to run attention over all N-1 previous tokens. Rather than recomputing keys and values for every previous token on each new step (which would be quadratic in time), the model caches them. This is the KV cache.

KV cache size formula:

KV cache = 2 × n_layers × n_kv_heads × head_dim × context_length × bytes_per_element

The 2 is for K and V separately. It grows linearly with context length. Worked example for Llama 3 8B (which uses GQA — explained below):

The table above assumes the worst case: FP16 KV cache stored entirely in VRAM, on a dense model with relatively many KV heads. Real inference engines close the gap significantly with three techniques:

KV cache quantization

llama.cpp can quantize the KV cache itself to Q8 or Q4. Q8 halves the cache size vs FP16. Q4 quarters it. This is what options like "turbo quant" enable — the 128K example above shrinks from 16GB to ~4GB at Q4 KV.

CPU RAM offloading

When VRAM fills, llama.cpp spills the KV cache into system RAM silently. Slower per token but functional. A 16GB GPU paired with 64GB of system RAM can handle very long contexts this way.

MoE architecture

MoE models often have fewer KV heads per parameter count than dense models, since the expert layers provide capacity that doesn't go through attention. A 35B MoE can have a smaller KV cache footprint than a 13B dense model.

The core point still holds: KV cache is the hidden VRAM cost that grows with context and catches people off guard. The specific numbers depend heavily on model architecture, KV quantization level, and how much of the cache gets offloaded to RAM.

3. Why llama.cpp lets you increase it beyond the training limit

llama.cpp exposes a parameter called --rope-freq-base (or equivalently --ctx-size with automatic scaling). Increasing this stretches the RoPE rotation angles so the model's positional encoding covers a longer range without completely collapsing outside its training distribution.

Techniques like YaRN and LongRoPE do this more carefully — they interpolate the position angles rather than extrapolating, which causes less quality degradation. Some models are specifically fine-tuned with these techniques to genuinely extend their context (Llama 3.1's 128K context was achieved this way from a shorter base).

The practical result: you can push most models 2–4× beyond their training context with modest quality loss on the extended portion. Beyond that the model starts losing coherence at the edges of the window because the positional signal is too far outside what it trained on.

GQA: the fix modern models use to shrink the KV cache

Older models (GPT-2, Llama 1) used one set of K and V heads per attention head. If you have 32 heads, you cache 32 sets of K and V. Grouped Query Attention (GQA) shares K and V across groups of query heads — Llama 3 8B uses 8 KV heads instead of 32, making the KV cache 4× smaller for the same model size and context length. The quality impact is minimal because query heads in the same group tend to attend to similar positions anyway.

This is why Llama 3 can run 128K context on a single GPU where Llama 2 at the same size could not — the architecture change reduced KV cache pressure by 4× before any other optimization.

Rule of thumb for VRAM planning
When loading a model, budget: model weights + (context_length × ~0.125–0.5 MB per token depending on model size and KV head count). For a 7B model at 32K context, the KV cache alone is typically 4–8 GB on top of the weights. If you are running out of VRAM mid-conversation, reduce context size first before reducing model size.

TurboQuant: pushing KV cache compression further

Standard KV cache quantization (Q8, Q4) rounds values to fewer bits but still needs to store quantization constants in full precision alongside the compressed data. Those constants add 1–2 extra bits per value and erode the compression benefit. TurboQuant is a Google Research paper (March 2026, Zandieh and Mirrokni) that eliminates this overhead with two techniques stacked together.

PolarQuant

Converts vectors from Cartesian coordinates to polar coordinates before quantizing. Standard quantization maps onto variable square grids, which requires storing normalization constants. Polar coordinates map onto a predictable circular grid, making those normalization constants unnecessary. Zero overhead for the grid constants.

QJL (Quantized Johnson-Lindenstrauss)

Reduces each vector component down to a single sign bit: +1 or -1. One bit per component, zero memory overhead for constants. A specialized estimator then reconstructs the attention scores from those sign bits with enough accuracy that quality is preserved. The math comes from Johnson-Lindenstrauss random projections, which guarantee that dot products between vectors are approximately preserved even after this extreme reduction.

Q & A

Q4 quantized large model vs smaller full-precision model: which is better?

Assuming both are recent, trained on similar data, and both fit in VRAM: the Q4 large model wins almost every time.

Why quantization loses less than you'd expect

Modern Q4 quantization (methods like GPTQ, AWQ, or GGUF Q4_K_M) rounds each weight from 16 bits down to 4 bits. That sounds like throwing away 75% of the information, but in practice the capability loss is small — typically 2–5% degradation on benchmarks — because the weights in a trained model are not uniformly distributed. Most weights cluster near zero and the quantization methods are designed to preserve the outliers that actually matter.

Halving the parameter count, on the other hand, loses substantially more. The model has fewer parameters to store knowledge in, shallower reasoning capacity, and weaker representations learned during training. That structural deficit cannot be recovered by using higher precision arithmetic on what remains.

Q4 large model

Loses ~2–5% capability from quantization. Keeps all the knowledge, reasoning depth, and representations learned from scale. A Q4 70B model consistently outperforms a FP16 13B model across almost all benchmarks.

Full-precision small model

Perfect numerical precision on a weaker foundation. The extra bits are being used to represent weights that already encode less knowledge. Precision cannot compensate for missing capacity.

Concrete benchmark pattern

This holds consistently across model families. On standard evals like MMLU, HumanEval, and HellaSwag:

The one case where the smaller model wins

Speed. More parameters means more compute per token. For the same batch size, the larger model produces tokens slower. If your application needs sub-100ms latency or you are running high-throughput inference where tokens/second matters more than raw quality, the smaller full-precision model can be the right trade-off. For most local use cases where you are waiting seconds per response anyway, this does not matter.

The other edge case is very aggressive quantization: Q2 and Q3 have large enough numerical errors that a smaller model in FP16 can sometimes compete depending on the task. Q4 is generally considered the safe floor where quality is well-preserved.

Practical Concepts

Data gathering and cleaning

Where data comes from

For general language models there are a handful of standard sources. You do not scrape the web yourself at this scale.

WEB

Common Crawl

The largest freely available web scrape. Petabytes of raw text from billions of pages. Very dirty. Almost always used as the base, then heavily filtered. Most big models start here.

FILT

FineWeb / FineWeb-Edu

HuggingFace's filtered version of Common Crawl. FineWeb-Edu specifically filters for educational content using a classifier. Strong out-of-the-box quality. Good starting point for a first training run.

CURB

The Pile / RedPajama

Curated mixtures of web text, books, Wikipedia, academic papers, GitHub code. EleutherAI's Pile was widely used before FineWeb. RedPajama is an open reproduction of LLaMA's training mix.

HIGH

Wikipedia, books, arXiv

High-quality, low-volume. Dense information per token. Usually mixed in at a higher ratio than their raw size would suggest. Wikipedia alone is only ~20GB of text but punches above its weight in quality.

What cleaning actually involves

The level of cleaning needed depends on the source. Raw Common Crawl needs aggressive cleaning. Pre-filtered datasets like FineWeb need much less.

Always worth doing

Deduplication is the most important step. Duplicate text causes memorization, wastes training compute on redundant data, and can inflate benchmark scores. MinHash LSH is the standard approach at scale.

Worth doing

Language filtering with fastText. If you are training an English model, non-English text adds noise. Simple and fast to filter.

Situational

Quality filtering via heuristics: document length, ratio of symbols to words, ratio of repeated lines. Aggressive filtering can hurt if it removes valid but short documents.

Usually skip for research

PII removal (names, emails, phone numbers) matters for production models you deploy. For a research training run that stays local, the complexity is rarely worth it.

The counterintuitive finding from several papers: a small amount of high-quality data mixed with larger amounts of decent data often beats large amounts of heavily filtered data alone. LLaMA-1 used less filtered data than expected and still worked well. The data mixture matters as much as cleaning.

For this project specifically

Use FineWeb-Edu as your base. It is already deduplicated and quality-filtered. Add Wikipedia and a small slice of books if you want. That gets you a usable pretraining dataset without building a cleaning pipeline from scratch, which is a project in itself.

Practical Concepts

Finetuning vs training from scratch

For most practical use cases, yes. For learning what you are trying to learn here, no. The reason differs depending on what you are optimizing for.

Why finetuning wins in industry

A base model like LLaMA 3 8B has already seen roughly 15 trillion tokens. Your 75M model trained on 1B tokens will not beat it on any benchmark. The knowledge, reasoning, and language understanding in LLaMA 3 took tens of thousands of GPU-hours to build. You get that for free when you finetune.

Finetuning teaches the model new behavior on top of existing knowledge. Training from scratch makes it build all knowledge from scratch. For most tasks (instruction following, domain adaptation, style, classification), the behavior change is all you need.

Finetuning a 7B base model

Costs a few hours on your GPU. Starts with a model that already reads and reasons well. You direct it toward your task. Beats a from-scratch 75M model on virtually every downstream benchmark.

Training 75M from scratch

Costs 6-8 hours on your GPU for 1B tokens. Gives you a model that produces coherent text but has shallow knowledge. Necessary for learning the pipeline, not for building something useful.

The middle option: continual pretraining

Take an existing base model and keep pretraining it on your domain data before finetuning. Used when your domain is genuinely out-of-distribution from the base model's training data (e.g., a specific programming language, a clinical subdomain, a non-English language with limited web presence). The base model keeps its general capabilities while absorbing your domain knowledge more deeply than finetuning alone can achieve.

Why training from scratch still makes sense here

Training from scratch is not about producing the most capable model — it is about understanding how these systems work. Finetuning hides the whole stack below the surface. Training from scratch means you have written or understood every component: the architecture, the data pipeline, the training loop, the loss curve, the scaling behavior. That knowledge transfers to every model you work with afterwards, including the ones you finetune.

The practical split

In industry: almost nobody trains from scratch except frontier labs (OpenAI, Google, Meta, Anthropic, Mistral). Everyone else finetunes. In research: you train from scratch when you want to study the training process itself, scaling laws, or architecture decisions. This project falls squarely in the second category.

Training Concepts

What is loss, and what do the numbers mean?

Loss is not on a scale of 0 to 10. It is unbounded, and only makes sense relative to reference points.

The model predicts the next token by outputting a probability for every word in its vocabulary (50,257 words for GPT-2 tokenization). Loss measures how wrong those predictions are — specifically, it is cross-entropy loss: roughly, how surprised the model was when it saw the actual next word.

~10.8

Random guessing. Assigning equal probability to all 50,257 tokens gives ln(50257) ≈ 10.8. This is where every model starts.

~5.1

50M model, 5K steps, 80M tokens. Real English words and grammar — but sentences don't connect meaningfully across a paragraph.

~3.5

GPT-2 small (117M params, properly trained). Coherent paragraphs with some factual errors.

~1.5–2.5

SOTA models (LLaMA, GPT-4, Claude). Hard to distinguish from human writing at a glance.

A loss of 1.0 would mean the model narrows down the next word to about 3 plausible options on average — essentially reading the writer's mind. Open-ended natural language generation never reaches this. Sub-1 loss only appears in highly constrained tasks (e.g., predicting the next byte in a compressed file).

Why loss drops fast at first then slows

Early in training, the model learns obvious things: spaces come after words, capital letters follow periods, "the" is extremely common. These easy patterns produce fast loss drops. Later improvements require understanding context, facts, and reasoning — much harder to compress into weights, so each additional drop costs exponentially more compute.

Loss vs perplexity

Perplexity is just eloss. A loss of 5.1 = perplexity of ~164, meaning the model is as confused as if it had to choose uniformly from 164 options at each step. A loss of 2.3 = perplexity of 10, meaning it narrows it to about 10 plausible next words. Most papers report perplexity; training logs report loss. They carry the same information.

train_step — how the model actually learns

model.py defines what the model is. train_step() defines what happens every time it sees a batch of data. The model itself never changes during a forward pass — only train_step updates the weights.

model.py vs train.py in one line:
model.py = the engine. train_step = turning the key, measuring how far off you are, and adjusting the engine slightly. Repeat billions of times.

The code

def train_step(model, optimizer, x, y, config, scaler): with torch.autocast(device_type="cuda", dtype=torch.bfloat16): logits, loss = model(x, y) loss = loss / config.gradient_accumulation_steps scaler.scale(loss).backward() scaler.unscale_(optimizer) torch.nn.utils.clip_grad_norm_(model.parameters(), config.grad_clip) scaler.step(optimizer) scaler.update() optimizer.zero_grad(set_to_none=True) return loss.item() * config.gradient_accumulation_steps

What happens in order

1
Forward pass
Tokens go through the model. Each block refines the representations. lm_head produces a score for every vocab word. Cross-entropy compares those scores against the real next tokens and produces one loss number.
2
Backward pass
PyTorch walks backwards through every operation that produced the loss, computing a gradient for each weight. The gradient says: "if you increase this weight, loss goes up/down by this much."
3
Gradient clip
If any gradient is unusually large (bad batch, early training instability), scale all gradients down. Prevents one bad step from destroying training progress.
4
Weight update
AdamW uses each weight's gradient (and its history of past gradients) to nudge the weight slightly in the direction that reduces loss. Then gradients are cleared ready for the next batch.

This cycle repeats for every batch — thousands of times. Each repetition adjusts the weights by a tiny amount. After enough steps, those tiny adjustments add up to a model that has learned grammar, facts, and reasoning patterns from the data.
