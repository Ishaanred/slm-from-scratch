Phase 2 — Tokenization

Tokenization and BPE

Before a language model sees any text, that text has to be converted into numbers. Tokenization is that conversion. It turns a string of characters into a sequence of integer IDs the model can process.

This page explains how that works, why the naive approaches fail, and how BPE (byte-pair encoding) solves both problems at once.

🔢

What you will understand

Why models can't read raw text, what BPE does step by step, and how vocabulary size affects training.

⚙️

What you will build

A BPE tokenizer trained on your own corpus using HuggingFace tokenizers. Your model will use it instead of GPT-2's tokenizer.

📐

Why it matters

A better tokenizer compresses text more efficiently — fewer tokens per idea means more context fits in the same sequence length.

The Problem

What is tokenization

A transformer model operates on sequences of integers. It cannot read the string "hello world" directly. Every piece of text needs to be mapped to a list of integer IDs before training or inference can happen.

Tokenization is the step that does that mapping:

TEXT
"The cat sat on the mat"
TOKENS
The cat sat on the mat
TOKEN IDs
[ 464, 3797, 3332, 319, 262, 2603 ]

The model only ever sees the integer list. The embeddings table converts each integer into a vector. The model never processes raw characters.

The vocabulary is the set of all possible tokens. Every token has an ID (its index in the vocabulary). The tokenizer is the function that splits text into tokens and returns their IDs.

The Naive Approaches

Why not just use characters

The simplest possible tokenizer would split every character into its own token. "hello" becomes [h, e, l, l, o].

What works

Vocabulary is tiny — just the 256 ASCII characters or ~130K Unicode points. Every word is representable, even ones you never saw in training.

What breaks

Sequences get extremely long. "The cat sat" becomes 11 tokens instead of 3. The model's context window fills up faster, and learning word-level meaning from individual characters is very hard.

Concretely: GPT-2 has a 1024 token context window. At the character level, that fits about 200 words — barely two paragraphs. At the word/subword level, it fits about 700 words. The character model sees 3x less text per forward pass.

There is also a deeper problem. The model needs to learn that c + a + t means cat, that c + a + t + s means multiple cats, and so on — entirely from attention patterns across characters. This is possible but wastes a lot of capacity on structure that could be captured at the token level.

Why not just use words

The other naive approach: split on whitespace. Each word is one token. "the cat sat" becomes [the, cat, sat].

What works

Sequences are short. Each token carries semantic meaning. Easy to understand what each ID represents.

What breaks

Vocabulary explodes. English alone has 500K+ words. Add names, technical terms, URLs, code, misspellings — you easily need millions of entries. Out-of-vocabulary words (anything not seen in training) get mapped to a single UNK token, destroying information.

The out-of-vocabulary problem is fatal. If someone writes "ChatGPT" and your tokenizer never saw it, it becomes [UNK]. The model has no idea what it means. Word-level tokenizers also treat run, runs, running, runner as four completely unrelated tokens, even though they share a root and meaning.

The tradeoff

Characters: tiny vocab, very long sequences, hard to learn meaning. Words: short sequences, vocabulary explosion, out-of-vocab failure. You want something in between.

The Solution

How BPE works

BPE stands for byte-pair encoding. The name comes from a data compression algorithm from the 1990s. The core idea: start with individual characters, then repeatedly merge the most common adjacent pair into a single new token.

Think of it like learning shorthand. You start by writing every letter separately. Then you notice you always write "th" together, so you invent a symbol for it. Then you notice "the" is common, so you invent a symbol for that. You keep going until your shorthand system has the right number of symbols for the vocabulary size you want.

Vocab size
When you hit your target vocabulary size

The vocabulary size is a hyperparameter you choose before training the tokenizer. Common values: 8K (small, aggressive compression), 32K (GPT-2, balanced), 50K (GPT-2 actual), 100K+ (modern models like LLaMA 3).

The result is a vocabulary of subword tokens — fragments that are smaller than words but larger than characters. Common words get their own token. Rare words get split into recognizable pieces. Nothing becomes UNK.

BPE

Step by step example

Let's train a tiny BPE tokenizer on one sentence: "low lower lowest". In a real tokenizer you'd use gigabytes of text — the algorithm is identical, just larger.

Initial state — every character is a token, words end with a special end marker
l o w </w>  |  l o w e r </w>  |  l o w e s t </w>
Count all adjacent pairs across the corpus
(l,o): 3 times  |  (o,w): 3 times  |  (w,</w>): 1 time  |  (w,e): 2 times  |  (e,r): 1 time  |  (e,s): 1 time ...
Merge #1 — most common pair is (l, o) with 3 occurrences
lo w </w>  |  lo w e r </w>  |  lo w e s t </w>
Merge #2 — now (lo, w) is most common with 3 occurrences
low </w>  |  low e r </w>  |  low e s t </w>
Merge #3 — (low, </w>) and (w, e) both have 2 occurrences, pick one
low</w>  |  low er </w>  |  low e s t </w>

After enough merges you end up with tokens like low, lower, er, est. Common complete words get their own token. Rare words are split into pieces that appear in many other words — so the model still has some signal about what they mean.

The merge list is the tokenizer

When you train a BPE tokenizer, you produce a list of merge rules in the order they were learned. At inference time, to tokenize new text, you apply those same merges in the same order. The tokenizer is deterministic — the same string always produces the same token IDs.

BPE

Special tokens

Every tokenizer has a handful of tokens that aren't text — they carry structural meaning. You define these before training and they get reserved IDs.

<|endoftext|>

Marks the boundary between documents. Without this, the model doesn't know where one article ends and the next begins. You saw this in your Phase 1 output — the model generated it mid-sequence when it "decided" to start a new document.

<|pad|>

Padding token. When batching sequences of different lengths, shorter ones get padded to match the longest. The model should ignore these positions — handled via attention masking.

<|bos|> / <|eos|>

Beginning/end of sequence. Some models use these instead of endoftext. Marks where generation should start and stop.

<|unk|>

Unknown token. With byte-level BPE (below) this should never appear — every possible byte sequence is representable. Still included for compatibility.

BPE

Byte-level BPE

Standard BPE starts from characters. Byte-level BPE starts from raw bytes instead. Every possible byte value (0–255) is a starting token.

Why bytes instead of characters? Because characters are ambiguous. Unicode has over 140,000 characters. Some are rare enough that a character-level vocabulary would either omit them (forcing UNK) or bloat the starting vocabulary unnecessarily. Bytes sidestep this entirely — every possible input, in any language, in any encoding, is representable as a sequence of bytes. There is no UNK.

This is what GPT-2 and most modern tokenizers use

Byte-level BPE means the tokenizer can handle any Unicode text, code, emoji, URLs, and arbitrary bytes without ever producing an unknown token. The HuggingFace ByteLevelBPETokenizer implements this.

In Practice

Compression ratio

The key metric for a tokenizer is how many tokens it produces per 1000 characters of text. Fewer tokens = more efficient = more text fits in the context window = cheaper training.

Same sentence through different tokenizers:

"The quick brown fox jumps over the lazy dog."

Character-level (45 tokens)
The quick brown... 30 more
GPT-2 tokenizer (10 tokens)
Thequickbrownfoxjumpsoverthelazydog.
Well-trained 32K tokenizer (~8 tokens)
Thequickbrownfoxjumpsoverthelazy dog.

When you train your tokenizer, calculate its compression ratio on a held-out text sample and compare it to GPT-2. If yours is lower (fewer tokens for the same text), it is encoding information more efficiently.

In Practice

HuggingFace tokenizers library

The tokenizers library is written in Rust and wrapped in Python. Training a tokenizer that would take hours in pure Python takes minutes here. It is what GPT-2, LLaMA, and most production tokenizers were built with.

The key components:

ByteLevelBPETokenizer

Handles the byte-level BPE algorithm. You pass it a corpus, a vocab size, and it does all the merges and produces the tokenizer files.

BpeTrainer

Lower-level trainer if you want more control — custom special tokens, minimum frequency cutoffs, or a different initial alphabet.

vocab.json

The vocabulary: a mapping from token string to integer ID. This is what gets loaded at inference time.

merges.txt

The merge rules in the order they were learned. To tokenize new text, apply these merges in order from top to bottom.

Once trained, you load it with tokenizers.Tokenizer.from_file() or wrap it in a HuggingFace PreTrainedTokenizerFast to get the full HF interface.

∑ Training API sketch
from tokenizers import ByteLevelBPETokenizer tokenizer = ByteLevelBPETokenizer() tokenizer.train( files=["data/corpus.txt"], vocab_size=32_000, min_frequency=2, special_tokens=["<|endoftext|>", "<|pad|>"] ) tokenizer.save_model("src/tokenizer_/") # saves vocab.json and merges.txt
Q&A

Why does "king" tokenize differently than "King"? Q

BPE is case-sensitive by default. king and King are different byte sequences, so they can end up as different tokens — or one might get split while the other doesn't, depending on how frequently each appeared during tokenizer training.

This is also why some models are case-sensitive in ways that feel arbitrary. If King appears less often in the training corpus than king, it might not have earned its own merge and gets split into K + ing while king stays as one token.

The downstream effect

Because "King" and "king" are different token IDs, the model has to learn separately that they refer to the same concept. This is one reason why training on lowercased text can sometimes improve performance for small models — it reduces the vocabulary duplication. Modern large models have enough capacity to handle it without preprocessing.

Q&A

Why are numbers and dates so weird? Q

Try tokenizing 1234567 with GPT-2. You might get [12, 345, 67] or [1, 234, 567] or something else entirely depending on how those digit sequences happened to appear in the training corpus.

Numbers are a known weakness of BPE. Because BPE merges based on frequency, common number patterns (years like 1990, 2023; round numbers like 1000) get their own tokens, while arbitrary numbers get split unpredictably. The model then has to do arithmetic across token boundaries that don't respect place value — a very hard thing to learn.

This is one reason LLMs are bad at arithmetic. It is not fundamentally a model size problem — it is a tokenization problem. Dedicated number tokenizers (e.g., always split each digit individually) help, but most general-purpose tokenizers don't bother.

Q&A

Why do non-English languages use more tokens? Q

If a tokenizer is trained mostly on English text, the merge rules reflect English frequency patterns. Common English words and subwords get merged into single tokens. Non-English words — which appear far less often in the corpus — don't accumulate enough frequency to earn merges, so they get split into smaller and smaller pieces.

In extreme cases, languages with non-Latin scripts (Arabic, Chinese, Korean, Thai) can produce 5-10x more tokens than English for text that carries the same amount of information. This makes those languages effectively more expensive to process — the model spends more of its context window on the same content.

The fix is to include more of those languages in the tokenizer training corpus, so their patterns earn their own merges. LLaMA 3's 128K vocabulary was partly motivated by improving multilingual tokenization efficiency.

For this project

OpenWebText is English-dominated, so your tokenizer will be English-efficient. That is fine for the current goal. If you wanted multilingual capability later, you would need to add multilingual data to the tokenizer training corpus.
