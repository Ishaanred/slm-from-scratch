Phase 2: Tokenization + Data Engineering

The model is done.
Now feed it properly.

Phase 1 built the engine. Phase 2 decides what fuel goes in and what language the engine thinks in. This is where most of the real quality difference between models comes from.

Start here

Phase 2 from start to finish

Everything else on this page is a piece of one pipeline. You start with raw text and end with your own tokenizer plus a clean, tokenized dataset that Phase 3 will train on. Each step produces the input the next step needs, which is why the order matters. The concept sections further down explain the why behind each step. This is the what, in order.

1

Get a raw text sample

Carve 1 to 2 GB of plain text out of the OpenWebText shards you already have. This is the input for everything downstream: both the filters and the tokenizer trainer read raw text, so it has to exist first.

2

Clean the text

Run the filtering pipeline: language filter, then quality heuristics, then exact and near deduplication. This comes before training the tokenizer for a concrete reason: the tokenizer learns its vocabulary from whatever text you feed it. Feed it spam and boilerplate and it spends merges memorising junk. Clean first so the merges reflect real language.

Concepts: garbage in, garbage out, the filtering pipeline
3

Train the BPE tokenizer

Run byte-level BPE on the clean text, with your chosen special tokens, at a few candidate vocabulary sizes (8K, 16K, 32K). This produces the merge rules and vocabulary. It depends on step 2 because the merges are only as good as the text they were learned from.

Concepts: how BPE works, vocabulary size, special tokens, byte-level BPE, the tokenizers library
4

Evaluate and pick a vocab size

Measure the compression ratio of each candidate against GPT-2's tokenizer on held-out text, and pick the best tradeoff between fewer tokens and a bigger embedding table. This step turns step 3's three candidates into one chosen tokenizer.

Concepts: compression ratio, why train your own
5

Tokenize the clean corpus

Run the chosen tokenizer over the cleaned data to produce new train.bin and val.bin, replacing the GPT-2-tokenized versions from Phase 1. This is the actual dataset every Phase 3 training run will read.

6

Verify with a short run

Train for about 1,000 steps on the new data and confirm the loss behaves like Phase 1. This is a cheap sanity check that catches pipeline bugs (a broken vocab, a tokenization mismatch) before you commit GPU hours to long runs.

The thread: raw text becomes clean text (step 2), clean text teaches the tokenizer (step 3), the tokenizer is chosen by measurement (step 4), the chosen tokenizer rewrites the dataset (step 5), and a short run proves the dataset works (step 6). Every section below this is the reasoning behind one of these moves.

A note on order

Steps 2 and 3 have a real dependency, but in practice you can overlap them. Filtering a large corpus can run unattended for hours, so it is fine to train a throwaway tokenizer on the raw sample first just to see the mechanics work, then retrain the real one on the filtered text once step 2 finishes. The dependency is about which tokenizer you keep, not which you run first.

Overview

What changed from Phase 1

Phase 1 was about controlling the model: how many layers, how wide, what the attention mechanism does, how the training loop runs. You wrote all of that. The data was a given.

Phase 2 flips that. The model is already written. Now the question is what does it learn from, and in what language does it think.

Phase 1

You controlled the model

  • Architecture: layers, heads, embedding size
  • Training loop: LR schedule, batch size, grad accum
  • Optimizer: AdamW, weight decay
  • Data: borrowed GPT-2 tokenizer, raw OpenWebText
Phase 2

You control the data

  • Tokenizer: what the vocabulary is, how text splits
  • Quality: what counts as a good training example
  • Deduplication: how much repetition is in the corpus
  • Language: what kind of text the model learns from

Both phases affect model quality. But at this scale, bad data beats bad architecture. A well-trained transformer on clean data will outperform a larger, better-tuned model on noisy data every time.

Overview

What is tokenization

A transformer operates on sequences of integers. It cannot read the string "hello world" directly. Every piece of text has to be mapped to a list of integer IDs before training or inference can happen.

Tokenization is that mapping. It turns a string of characters into a sequence of IDs the model can process:

Text input
"The cat sat on the mat"
Tokens
The cat sat on the mat
Token IDs
[ 464, 3797, 3332, 319, 262, 2603 ]

The model only ever sees the integer list. The embedding table converts each integer into a vector. The model never processes raw characters.

The vocabulary is the set of all possible tokens. Every token has an ID, which is its index in the vocabulary. The tokenizer is the function that splits text into tokens and returns their IDs.

Tokenizer Basics

Why not just use characters

The simplest possible tokenizer splits every character into its own token. "hello" becomes [h, e, l, l, o].

What works

Vocabulary is tiny: just the 256 ASCII bytes or ~130K Unicode points. Every word is representable, even ones never seen in training. No out-of-vocabulary problem.

What breaks

Sequences get extremely long. "The cat sat" becomes 11 tokens instead of 3. Context windows fill up faster, and learning word-level meaning from individual characters is very hard.

Concretely: GPT-2 has a 1024-token context window. At character level that fits about 200 words, barely two paragraphs. At subword level it fits about 700 words. The character model sees 3x less text per forward pass.

There is also a deeper problem. The model has to learn that c + a + t means cat, and c + a + t + s means multiple cats, entirely from attention patterns across individual characters. That wastes capacity on structure the tokenizer could handle instead.

Tokenizer Basics

Why not just use words

The other naive approach: split on whitespace. Each word is one token. "the cat sat" becomes [the, cat, sat].

What works

Sequences are short. Each token carries semantic meaning. Easy to understand what each ID represents.

What breaks

Vocabulary explodes. English alone has 500K+ words. Add names, technical terms, URLs, code, misspellings and you easily need millions of entries. Out-of-vocabulary words collapse to a single UNK token, destroying the information.

The out-of-vocabulary problem is fatal at inference time. If a user writes "ChatGPT" and the tokenizer never saw it, it becomes [UNK]. The model has no idea what it means. Word-level tokenizers also treat run, runs, running, runner as four completely unrelated tokens, even though they share a root and meaning.

The tradeoff so far: Characters give a tiny vocab but very long sequences and slow learning. Words give short sequences but a vocabulary explosion and OOV failure. You need something in between: subword tokenization.
BPE

How BPE works

BPE stands for byte-pair encoding. The name comes from a lossless compression algorithm. The idea: start with individual characters, then repeatedly merge the most common adjacent pair into a single new token.

Analogy: Learning shorthand. You start writing every letter separately. Then you notice you always write "th" together, so you invent one symbol for it. Then "the" is common, so you invent a symbol for that. You keep going until the shorthand system has the right number of symbols for your vocabulary size.

Vocab size
When you hit your target vocabulary size

The vocabulary size is a hyperparameter you choose before training. Common values: 8K (small, aggressive), 32K (GPT-2 range, balanced), 128K (modern models like LLaMA 3). The result is a vocabulary of subword tokens, fragments smaller than words but larger than characters. Common words get their own token. Rare words split into recognizable pieces. Nothing becomes UNK.

BPE

Step by step example

Training a tiny BPE tokenizer on one sentence: "low lower lowest". In a real tokenizer you'd use gigabytes of text, but the algorithm is identical, just larger.

Initial state: every character is its own token; words end with a boundary marker
l o w </w>  |  l o w e r </w>  |  l o w e s t </w>
Count all adjacent pairs across the corpus
(l, o): 3  |  (o, w): 3  |  (w, </w>): 1  |  (w, e): 2  |  (e, r): 1  |  (e, s): 1
Merge #1: most frequent pair is (l, o) with 3 occurrences
lo w </w>  |  lo w e r </w>  |  lo w e s t </w>
Merge #2: now (lo, w) is most frequent with 3 occurrences
low </w>  |  low e r </w>  |  low e s t </w>
Merge #3: (w, e) appears twice; merge it into "we"
low </w>  |  low er </w>  |  low e s t </w>

After enough merges you end up with tokens like low, er, est. Common complete words get their own token. Rare words are split into pieces that appear in other words, so the model still has signal about their meaning.

The merge list is the tokenizer

When you train a BPE tokenizer, you produce a list of merge rules in the order they were learned. To tokenize new text, apply those same merges in the same order. The tokenizer is deterministic. The same string always produces the same token IDs.

BPE

Vocabulary size

Analogy: A small dictionary forces you to explain things in more words. A large dictionary has a word for everything but takes longer to look up. There is a sweet spot for your corpus.

The number of merges determines vocabulary size. Each merge adds one new token. Start with 256 byte tokens and do 31,744 merges and you get a 32K vocabulary. Larger vocabulary means fewer tokens per sentence (better compression), but a bigger embedding table.

BPE

Special tokens

Every tokenizer has a handful of tokens that aren't text. They carry structural meaning. You define these before training and they get reserved IDs.

<|endoftext|>

Marks the boundary between documents. Without this, the model doesn't know where one article ends and the next begins. You saw this in your Phase 1 output: the model generated it mid-sequence when it "decided" to start a new document.

<|pad|>

Padding token. When batching sequences of different lengths, shorter ones are padded to match the longest. The model ignores these positions via attention masking.

<|bos|> / <|eos|>

Beginning and end of sequence. Some models use these instead of endoftext. Marks where generation starts and where the model should stop.

<|unk|>

Unknown token. With byte-level BPE this should never appear, because every possible byte sequence is representable. Still included for compatibility.

BPE

Byte-level BPE

Standard BPE starts from characters. Byte-level BPE starts from raw bytes instead. Every possible byte value (0–255) is a starting token.

Why bytes instead of characters? Because characters are ambiguous. Unicode has over 140,000 characters. Some are rare enough that a character-level vocabulary would either omit them (forcing UNK) or bloat the starting set unnecessarily. Bytes sidestep this entirely. Every possible input in any language, encoding, emoji, or URL is representable as a sequence of bytes. There is no UNK.

This is what GPT-2 and most modern tokenizers use

Byte-level BPE means the tokenizer can handle any Unicode text, code, emoji, URLs, and arbitrary bytes without ever producing an unknown token. The HuggingFace ByteLevelBPETokenizer implements this.

GPT-2's byte-level implementation maps the 256 raw bytes to 256 printable Unicode characters before doing BPE merges. This means the vocabulary only contains printable characters in the merge list. The actual byte-to-character mapping is a fixed lookup table. The HuggingFace ByteLevelBPETokenizer handles this for you automatically.
In Practice

Why train your own tokenizer

Three concrete reasons GPT-2's tokenizer is not the right choice for a custom training run:

1

Compression efficiency

GPT-2's vocabulary was trained on a specific slice of the internet in 2019. Common words in your dataset might split into more tokens than necessary, wasting sequence capacity. Your tokenizer learns the actual distribution of your corpus.

Example: a coding-focused tokenizer would encode "function", "return", "const" as single tokens. GPT-2 splits some of these.
2

Vocabulary ownership

When you borrow someone else's tokenizer, you inherit their vocabulary size (50,257 for GPT-2) and can't change it. Training your own lets you choose: 8K, 16K, 32K. That number affects your embedding table size and parameter count.

3

Special token control

You decide what special tokens exist. GPT-2 has one: <|endoftext|>. For a custom model you might want pad tokens, separator tokens, or instruction markers. These have to be in the vocabulary from the start. You can't add them later without re-training.

In Practice

Compression ratio

The key metric for a tokenizer is how many tokens it produces per 1000 characters. Fewer tokens means more text fits in the same context window and cheaper training.

Same sentence through different tokenizers
"The quick brown fox jumps over the lazy dog."
Character-level (45 tokens)
The quick brown... 30 more
GPT-2 tokenizer (10 tokens)
The quick brown fox jumps over the lazy dog.
Well-trained 32K tokenizer (~8 tokens)
The quick brown fox jumps over the lazy dog.

When you train your tokenizer, calculate its compression ratio on a held-out text sample and compare it to GPT-2. If yours is lower (fewer tokens for the same text), it is encoding information more efficiently. This is the first number to check after training.

In Practice

HuggingFace tokenizers library

The tokenizers library is written in Rust and wrapped in Python. Training a tokenizer that would take hours in pure Python takes minutes here. It's what GPT-2, LLaMA, and most production tokenizers were built with.

ByteLevelBPETokenizer

Handles the byte-level BPE algorithm. Pass it a corpus, a vocab size, and it runs all the merges and saves the tokenizer files.

BpeTrainer

Lower-level trainer for more control: custom special tokens, minimum frequency cutoffs, or a different initial alphabet.

vocab.json

The vocabulary: a mapping from token string to integer ID. This is what gets loaded at inference time.

merges.txt

The merge rules in the order they were learned. To tokenize new text, apply these merges in order from top to bottom.

Once trained, load it with tokenizers.Tokenizer.from_file() or wrap it in a HuggingFace PreTrainedTokenizerFast to get the full HF interface.

from tokenizers import ByteLevelBPETokenizer tokenizer = ByteLevelBPETokenizer() tokenizer.train( files=["data/corpus.txt"], vocab_size=32_000, min_frequency=2, special_tokens=["<|endoftext|>", "<|pad|>"] ) tokenizer.save_model("src/tokenizer_/") # saves vocab.json and merges.txt
Data Quality

Garbage in, garbage out

Analogy: Training a chef by making them read 10,000 recipes. If 3,000 of those are spam restaurant menus, duplicate listicles, and broken HTML, the chef learns those patterns too. A smaller set of real recipes produces a better cook.

OpenWebText contains 8.5 billion tokens scraped from URLs that Reddit users upvoted. "Upvoted by Reddit" is not the same as "high quality text." Here is what is actually in there:

removeBuy cheap Rolex watches free shipping click here now !!!
removeLorem ipsum dolor sit amet consectetur adipiscing elit sed do eiusmod...
remove&nbsp;&nbsp;&nbsp;Copyright © 2018 All Rights Reserved | Privacy Policy
removeThis article is the same as this article. This article is the same as this article.
keepThe paper describes a new approach to federated learning that reduces communication overhead...
keepScientists discovered that the protein responsible for cellular repair also plays a role in...

The model has no way to tell the difference during training. Every token counts equally toward the loss. If 20% of your tokens are junk, the model spends 20% of its capacity learning junk patterns.

Filtering does not remove content the model would find useful. It removes content where the signal-to-noise ratio is so low that learning from it actively competes with learning from better examples.

Data Quality

The filtering pipeline

Sprint 2B is four operations run in sequence. Each removes a different type of noise:

1

Language filtering

Keep only English documents. OpenWebText is mostly English but not entirely. Non-English text dilutes the vocabulary and makes the model's English worse unless you explicitly want multilingual capability.

Tool: fastText language detection. Runs on CPU, handles 176 languages, very fast.
2

Quality heuristics

Remove documents under 100 words, documents with an unusually high ratio of symbols or numbers to words, and documents that look like navigation menus or boilerplate HTML. Simple rules but they catch a large fraction of the junk.

3

Exact deduplication

Hash every document and drop identical copies. Web crawls pick up the same article from dozens of mirror sites. The model does not need to memorise the same paragraph 40 times.

4

Near-deduplication

MinHash LSH finds documents that are highly similar but not identical: the same story rewritten with slight changes, or SEO articles on the same topic. More expensive than exact dedup but catches a second layer of redundancy.

Tool: text-dedup library. Runs on CPU, works on datasets of any size.

After filtering, you inspect 100 random samples manually. Every serious ML team does this. It's how you find out what you actually filtered out and whether the heuristics removed something they should not have.

Build it

How to actually do it

Everything above is the reasoning. This is the code, one block per step of the roadmap. The files you end up with:

# new files data/sample_corpus.py # step 1: carve a text sample data/filter.py # step 2: clean it src/tokenizer_/train_tokenizer.py # step 3 src/tokenizer_/evaluate_tokenizer.py # step 4 data/prepare.py # step 5: edited to use your tokenizer

The code assumes the OpenWebText dataset is already on disk at data/openwebtext/ from Phase 1. Each block is small on purpose: the point is to read it and understand every line, not to run a black box.

Build it · Step 1

Sample a corpus

You do not need all 8 million documents to train a tokenizer or to test filters. A couple of gigabytes is plenty, and it keeps iteration fast. This reads the OpenWebText dataset from disk and writes one document per line to a plain text file, which is the format the tokenizer trainer and the filters both expect.

# data/sample_corpus.py import os from datasets import load_from_disk DATA = os.path.dirname(os.path.abspath(__file__)) ds = load_from_disk(os.path.join(DATA, "openwebtext")) N_DOCS = 200_000 # ~1-2 GB of text, enough for a tokenizer out = os.path.join(DATA, "sample.txt") with open(out, "w", encoding="utf-8") as f: for i in range(N_DOCS): text = ds[i]["text"].strip() if text: f.write(text.replace("\n", " ") + "\n") # one doc per line print(f"wrote {N_DOCS:,} docs to {out}")

The replace("\n", " ") flattens each document onto a single line so that one line equals one document. That matters in step 2, where the filters decide keep-or-drop per line.

Build it · Step 2

Filter the text

Three passes in one file: language detection, quality heuristics, and exact deduplication. Each function returns True for "keep" and False for "drop." Running them as a chain means a document has to pass all three to survive.

Language detection uses fastText's small model. Download it once: it lives at lid.176.bin on the fastText site. Install the library with pip install fasttext-wheel.

# data/filter.py import hashlib, fasttext lang = fasttext.load_model("lid.176.bin") def is_english(text): label, prob = lang.predict(text, k=1) return label[0] == "__label__en" and prob[0] > 0.65 def passes_quality(text): words = text.split() if len(words) < 100: # too short to be useful return False n = max(len(text), 1) if sum(c in "{}[]<>|@#^*_=~" for c in text) / n > 0.10: # symbol/SEO junk return False if sum(c.isdigit() for c in text) / n > 0.30: # number spam return False return True seen = set() def is_new(text): # exact dedup via content hash h = hashlib.md5(text.encode()).hexdigest() if h in seen: return False seen.add(h) return True kept = total = 0 with open("data/sample.txt") as fin, open("data/clean.txt", "w") as fout: for line in fin: total += 1 t = line.strip() if t and is_english(t) and passes_quality(t) and is_new(t): fout.write(t + "\n") kept += 1 print(f"kept {kept:,}/{total:,} ({100*kept/total:.1f}%)")

The thresholds (100 words, 10% symbols, 30% digits, 0.65 language confidence) are starting guesses, not laws. This is the judgment-call part of the phase: run it, open clean.txt, read what survived and what got cut, then adjust. Near-deduplication (catching near-identical rewrites, not just exact copies) is heavier and best handled by a dedicated library rather than hand-rolled. Run text-dedup with MinHash over clean.txt as a separate pass once exact dedup looks right.

Look at the data

Before moving on, actually open 100 random lines of clean.txt. This is the single highest-value habit in data engineering. It is how you catch a heuristic that is silently deleting good documents, or junk that slipped through.

Build it · Step 3

Train the tokenizer

This is the core of the phase. ByteLevelBPETokenizer does the byte-level BPE described earlier: it starts from raw bytes and merges frequent pairs until it hits the vocabulary size. You train three sizes so you can compare them in the next step. Each one saves a vocab.json, a merges.txt, and a single combined tokenizer.json that step 5 loads.

# src/tokenizer_/train_tokenizer.py import os from tokenizers import ByteLevelBPETokenizer for vocab_size in (8_000, 16_000, 32_000): tok = ByteLevelBPETokenizer() tok.train( files=["data/clean.txt"], vocab_size=vocab_size, min_frequency=2, # a pair must occur 2+ times to merge special_tokens=["<|endoftext|>", "<|pad|>"], ) out = f"src/tokenizer_/bpe_{vocab_size}" os.makedirs(out, exist_ok=True) tok.save_model(out) # vocab.json + merges.txt tok.save(f"{out}/tokenizer.json") # the full tokenizer in one file print(f"trained {vocab_size} -> {out}")

The special tokens are reserved before any merges happen, so they get stable low IDs. <|endoftext|> is the document boundary marker you append between documents when tokenizing the dataset in step 5. On a couple of GB this runs in minutes, which is the whole reason the library is written in Rust.

Build it · Step 4

Evaluate and pick a vocab size

The number that decides the winner is the compression ratio: tokens produced per 1,000 characters on held-out text. Fewer tokens means each token carries more text, so more fits in the same context window and training is cheaper. You compare your three candidates against GPT-2's tokenizer as a baseline.

# src/tokenizer_/evaluate_tokenizer.py from tokenizers import ByteLevelBPETokenizer from transformers import GPT2TokenizerFast sample = open("data/clean.txt").read()[:1_000_000] # 1M chars chars = len(sample) gpt2 = GPT2TokenizerFast.from_pretrained("gpt2") print(f"GPT-2 {len(gpt2.encode(sample))/chars*1000:6.1f} tok / 1k chars") for v in (8_000, 16_000, 32_000): tok = ByteLevelBPETokenizer( f"src/tokenizer_/bpe_{v}/vocab.json", f"src/tokenizer_/bpe_{v}/merges.txt", ) n = len(tok.encode(sample).ids) print(f"yours {v:<6} {n/chars*1000:6.1f} tok / 1k chars")

Lower is better, but bigger vocab always compresses better, so do not just pick 32K. Weigh the compression gain against the larger embedding table it forces (every extra token is another row of size n_embd in the model). For a 75M model, 16K is usually the sweet spot. Pick the size where the compression curve starts to flatten.

Build it · Step 5

Re-tokenize the dataset

Now point the data pipeline at your tokenizer instead of GPT-2's. This is a small edit to the Phase 1 data/prepare.py: swap the tokenizer, and read the end-of-text ID from your vocabulary. Everything else (the uint16 output, the train/val split) stays the same.

# data/prepare.py (the parts that change) from tokenizers import Tokenizer VOCAB = 16_000 # the size you picked in step 4 tok = Tokenizer.from_file(f"src/tokenizer_/bpe_{VOCAB}/tokenizer.json") eot = tok.token_to_id("<|endoftext|>") def tokenize(example): ids = tok.encode(example["text"]).ids ids.append(eot) # mark the document boundary return {"ids": ids, "len": len(ids)}

Run python data/prepare.py to regenerate train.bin and val.bin. These now hold your token IDs, not GPT-2's. uint16 holds values up to 65,535, so any vocab size up to that is fine.

The gotcha that breaks training

The model's vocab_size must equal your tokenizer's vocabulary size. Phase 1 used 50,257 (GPT-2). If you trained a 16K tokenizer, set vocab_size = 16_000 in the model config, or the embedding table and the token IDs will not line up and training will error out or produce garbage.

Build it · Step 6

Verify with a short run

Before committing GPU hours, run a tiny training job to prove the new pipeline works end to end. Set a short run and the matching vocab size in src/train.py:

# src/train.py -> TrainConfig max_iters: int = 1000 # short sanity run, not a real one vocab_size: int = 16_000 # MUST match your tokenizer

Then run it and watch the validation loss:

python data/prepare.py # rebuild bins with your tokenizer python src/train.py # 1k-step sanity run

What you are checking: does the loss start high and fall smoothly, landing somewhere near the Phase 1 ballpark? If yes, the tokenizer, the bins, and the model config all agree, and you are ready for the long Phase 3 runs. If the loss is flat, explodes, or starts absurdly high, you have a vocab-size mismatch or a broken tokenizer file, which is exactly what this cheap run is meant to catch.

Actual result (58.5M params, full 5,000-step run, not just the 1K sanity check): val loss fell smoothly from 10.55 → 5.23. See Phase 2 results and the Q&A below for why the raw number looks close to Phase 1's but isn't actually a fair comparison until you normalize for tokenizer differences.

Done with Phase 2: you now own a tokenizer tuned to your data and a clean, deduplicated dataset tokenized with it. Both feed straight into Phase 3, where the same pipeline runs at full scale for the scaling-law experiments.
Q&A

Questions

Why does "king" tokenize differently than "King"?

BPE is case-sensitive by default. king and King are different byte sequences, so they can end up as different tokens, or one might get split while the other doesn't, depending on how frequently each appeared during tokenizer training.

This is why some models behave differently with capital letters in ways that feel arbitrary. If King appears less often in the training corpus than king, it might not have earned its own merge and gets split into K + ing while king stays as one token.

The downstream effect

Because "King" and "king" are different token IDs, the model learns them separately. Training on lowercased text can sometimes improve performance for small models by reducing this duplication. Modern large models have enough capacity to handle it without preprocessing.

Why are numbers and dates so weird in LLMs?

Try tokenizing 1234567 with GPT-2. You might get [12, 345, 67] or [1, 234, 567] depending on how those digit sequences appeared in the training corpus.

Numbers are a known weakness of BPE. Because it merges based on frequency, common number patterns (years like 1990 or 2023, round numbers like 1000) get their own tokens, while arbitrary numbers split unpredictably. The model then has to do arithmetic across token boundaries that don't respect place value, which is a very hard thing to learn from examples alone.

This is one reason LLMs struggle with arithmetic. It is not a model size problem. It is a tokenization problem. Dedicated number tokenizers (always split each digit individually) help, but most general-purpose tokenizers don't bother.

Why do non-English languages use more tokens per idea?

If a tokenizer is trained mostly on English text, the merge rules reflect English frequency patterns. Common English words and subwords get merged into single tokens. Non-English words appear far less often and don't accumulate enough frequency to earn merges, so they get split into smaller and smaller pieces.

In extreme cases, languages with non-Latin scripts (Arabic, Chinese, Korean, Thai) can produce 5–10x more tokens than English for text carrying the same amount of information. This makes those languages effectively more expensive: the model spends more of its context window on the same content.

The fix is to include more of those languages in the tokenizer training corpus so their patterns earn their own merges. LLaMA 3's 128K vocabulary was partly motivated by improving multilingual tokenization efficiency.

OpenWebText is English-dominated, so your tokenizer will be English-efficient. That is fine for the current goal. If you wanted multilingual capability later, you would need to add multilingual data to the tokenizer training corpus.

Why not just use GPT-2's tokenizer for everything? It already works.

It does work. Phase 1 proved that. But "works" and "optimal" are different things.

GPT-2's vocabulary was designed for a specific dataset in 2019. The splits it chose reflect the frequency distribution of that corpus. If your corpus has different characteristics, some tokens will be used constantly and others almost never. That is wasted vocabulary capacity.

The deeper reason: training your own tokenizer means you understand what it decided and why. You will be able to look at how a sentence tokenizes and know whether it is doing the right thing. That understanding compounds through every later phase.

How much does data quality actually matter at this scale?

More than architecture at the 75M to 300M scale.

The Llama 2 models were smaller than GPT-3 and performed better on benchmarks. The main reason given was data quality, not architecture improvements. The Falcon and Mistral teams made similar claims. At scale, the gap between a carefully curated dataset and a raw web crawl is measurable in multiple benchmark points.

At your scale (75M, 1–2B tokens): you likely won't see a dramatic improvement from Phase 2 filtering alone, because the bottleneck right now is token count, not data purity. But the pipeline you build here is what you run before the Phase 3 and Phase 4 long training runs. That is when the quality difference shows up.

Why does this phase feel harder to plan than Phase 1?

Phase 1 had a clear correct answer at each step. Attention is implemented a specific way. The loss function is cross-entropy. Cosine LR with linear warmup is standard. You could look at nanoGPT and verify you did it right.

Phase 2 is full of judgment calls. What cutoff makes a document "too short"? How aggressive should the dedup threshold be? Which vocab size? There is no single correct answer. These decisions interact with your specific corpus, your model size, and what you want the model to be good at.

The practical answer: make a reasonable choice, run it, look at the data, adjust. You will iterate. That iteration is the learning. Phase 1 was about understanding a fixed system. Phase 2 is about building judgment.

Is data cleaning just running scripts? Take PII removal as an example.

PII (Personally Identifiable Information) is anything that can identify a real person: names, emails, phone numbers, home addresses, SSNs, credit card numbers, IP addresses. Raw web-scraped text always has some of this leaking in, and production training pipelines run a pass to scrub it out before training.

And yes, mostly it is just running scripts. Emails, phone numbers, SSNs, and credit cards all have predictable formats, so regex catches them cleanly. Less structured PII (names, addresses) gets caught with a pre-trained named-entity-recognition model, commonly Microsoft's presidio. Nobody is inventing a new detection algorithm here. It is a solved, library-call problem, the same way tokenizing is a library call once you've trained the tokenizer.

So where is the actual skill?

Not in the detection code. It's in the judgment around it:

  • Threshold tuning — too aggressive and you redact real content ("Elon Musk announced..." is a public figure's name, not something to scrub; a stranger's home address in a forum post is). Too lax and real PII slips through.
  • Context-dependent definitions — what counts as PII differs for a medical dataset vs. a general web scrape.
  • Sampling and review — no automated pass catches everything, and you cannot manually review a billion documents, so you spot-check samples and estimate an error rate instead.

This is the same shape as the rest of Phase 2, not a special case: the library call (train a tokenizer, run a filter, run a NER model) is trivial. The judgment calls — what threshold, what to keep, what a sample of your actual output looks like — are where the real work is. That's also why removing PII was cut from this project's Phase 2: it is a compliance concern for models that get deployed to real users. A 50-100M model trained on a small local sample and never served to anyone doesn't carry that risk, so the judgment call here was "not worth the time," not "too hard to automate."

Does the 128K vocabulary in GPT-4 and LLaMA 3 include other languages?

Yes. That is the main reason the number grew. Multilingual coverage is most of what those extra slots buy.

LLaMA 2 used a 32K vocabulary and was English-focused. LLaMA 3 jumped to 128K. GPT-4's cl100k_base is around 100K, and GPT-4o's o200k_base is around 200K. The jump was not because English needs more tokens. It was to make non-English text and code tokenize efficiently.

The vocabulary is one shared pool, not 128K per language. During tokenizer training you feed in a corpus that mixes many languages, and the merges get allocated in proportion to how much of each language is present. A language with lots of data earns many dedicated subword tokens. A language with little data earns few, and its text falls back toward byte-level fragments.

Analogy: One shared shorthand notebook for a multilingual office. The more memos written in a given language, the more dedicated shorthand symbols that language earns. Rare languages still get written down, just letter by letter, which takes more strokes.

For this project

Your corpus is English-dominated, so a 16K or 32K English-tuned vocabulary is the right call. You would only need a 128K-style vocabulary if you wanted real multilingual or heavy code capability, and that costs embedding-table VRAM you do not want to spend at 75M params.

How does it tokenize Hinglish, where someone mixes Hindi and English in one sentence?

Code-mixing is not a special case for the tokenizer. It tokenizes each piece of text with whatever merges apply, regardless of which language the piece came from. The interesting part is how efficiently each piece encodes, and that splits into two situations depending on the script.

Romanized Hindi (Latin script)

Most casual Hinglish is typed in Latin letters: "bro kal movie dekhne chalein". Because byte-level BPE starts from raw bytes and Latin letters are ordinary bytes, this never produces an unknown token. But the merges were learned mostly from English, so Hindi words only tokenize efficiently if they appeared often enough in the tokenizer's training data to earn their own merges. Social media text now contains so much Hinglish that frequent words like kya, nahi, bhai often do get single tokens. Rarer words split into fragments like de + kh + ne. The English words in the same sentence tokenize as normal.

Devanagari script

If the Hindi is written in its native script (कैसे हो), each character is several UTF-8 bytes, usually three. Byte-level BPE still represents it with no unknown token, but if the tokenizer saw little Devanagari it has no merges for it, so each character collapses toward two or three separate byte tokens. A short Hindi phrase can cost many more tokens than the same idea in English. This is the 5-10x inefficiency from the non-English question above, taken to an extreme.

The key idea

Byte-level BPE never fails on any script. There is no unknown token, ever. What changes is efficiency, and efficiency is decided entirely by how much of that language and script was in the tokenizer's training corpus. Handling Hinglish well is mostly a data problem, not a tokenizer-algorithm problem.

Whether the model then understands the Hinglish is a separate question answered by the training data, not the tokenizer. The tokenizer only decides how the text is chopped into IDs.

Why is the tokenizers library written in Rust and not Python?

Because tokenizing is a tight loop over an enormous amount of text, and that is exactly the kind of work Python is slow at. The fix is to move the hot loop out of Python and into compiled native code. Rust is the language HuggingFace chose for it.

Analogy: Counting every grain of rice in a warehouse. Doing it by hand (Python) works for a cup of rice but takes forever for a warehouse. A machine built for counting (Rust) does the same job orders of magnitude faster, and you can run many machines at once.
1

The work is a loop over billions of characters

Training BPE means counting every adjacent pair across gigabytes of text, then repeating thousands of merges. Encoding the corpus means chopping billions of tokens. Pure Python is interpreted and runs this kind of loop roughly 50 to 100 times slower than compiled code. What takes minutes in Rust takes hours in Python.

2

No GIL, so it uses every CPU core

Python's Global Interpreter Lock prevents true multithreading for CPU work. Rust has no such limit, so the library tokenizes batches in parallel across all your cores. This matters because if tokenization is slow, your expensive GPU sits idle waiting for data to train on.

3

Native speed with memory safety

Rust compiles to machine code like C, but without the buffer-overflow and segfault risks of C or C++, and with no garbage-collector pauses. You still write Python: the Rust core is wrapped in a Python API, so you get the speed underneath and the convenience on top.

It is not unique to Rust

The real requirement is "compiled native code, not pure Python." OpenAI's tiktoken is also written in Rust. Google's SentencePiece is written in C++. The common thread is keeping the hot loop out of the interpreter.

The Phase 2 verify run landed at val loss 5.23, almost the same as Phase 1's 5.24. Doesn't that mean nothing changed?

The two numbers looking close is a coincidence, not a result. Loss is measured per token, and Phase 1 (GPT-2's tokenizer) and Phase 2 (your own 32K tokenizer) chop the same text into different-sized tokens. Comparing raw loss across two different tokenizers is comparing two different units.

The actual compression numbers, measured on held-out text neither tokenizer was trained on:

GPT-2 (50,257) 227.2 tok / 1k chars (baseline) yours (32,000) 230.0 tok / 1k chars (-1.2% vs GPT-2, slightly worse)

Your 32K tokenizer takes marginally more tokens to represent the same text than GPT-2's — it doesn't compress better. That part is a clean, standalone finding: both tokenizers were run over the same held-out text, no model involved, no confound.

But converting the two training runs to bits-per-byte is a different claim, and this one is confounded:

Phase 1 (GPT-2 tokenizer): 1.718 bits/byte Phase 2 (your 32K tokenizer): 1.736 bits/byte

Don't over-read this one

Phase 1 trained on the full OpenWebText corpus (~8.5B tokens). Phase 2's train.bin came from the 200K-document sample sample_corpus.py pulls — a corpus explicitly sized "enough for a tokenizer," reused as the actual training corpus. After tokenizing it's only ~214M tokens: about 40x smaller than what Phase 1 trained on. So the two runs differ in two ways at once — tokenizer compression (a real, small ~1.2% effect) and training-corpus size (a ~40x difference, uncontrolled). A 0.018 bits/byte gap is fully explainable by corpus size alone. This result does not show the tokenizer hurt training — it only supports the standalone compression comparison above. A clean test would re-tokenize the full corpus with the 32K tokenizer and compare on equal data volume.

The bigger lesson isn't really about tokenizers — it's that a plausible-looking number (raw loss nearly matching) can hide two different problems at once (unit mismatch and a confounded comparison), and both need to be caught before trusting the conclusion.
