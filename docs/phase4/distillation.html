Context

What changed from Phase 3

Phase 3 was one model learning from raw text, at different scales. Phase 4 introduces a second model into the loop — a teacher whose outputs become part of the student's training signal, not just its architecture.

Phase 3

One model, raw text

  • Loss = compare prediction to the actual next token
  • Only one thing decides the learning signal: the corpus
  • Bigger/more data was the only lever
Phase 4

Two models, teacher + student

  • Loss can also compare student's guess to teacher's full guess distribution
  • A second signal enters: what the teacher was uncertain about
  • The lever is which loss variant, and how much to trust the teacher
Concept

What is distillation

Knowledge distillation trains a small "student" model to imitate a large "teacher" model's outputs, instead of (or in addition to) learning purely from raw text. The student never sees the teacher's weights or architecture — only what the teacher predicts, for the same inputs the student is training on.

Analogy: Two students studying for the same exam. One only has the textbook and works out every practice problem from first principles. The other has that textbook and a worked answer key from the best student in the class, showing not just the final answer but how confident that student was between every option on a multiple-choice question. The second student usually learns faster, because the answer key encodes information the textbook alone doesn't — which wrong answers were "almost right."

That "almost right" information is the whole point, and it's what the next section is actually about.

Concept

Hard labels vs soft labels

Training on raw text (Phases 1-3) is hard-label training: for "the cat sat on the ___", the target is just the single correct token, "mat", full credit or nothing. Every other word in the vocabulary gets the same zero signal, whether it was "rug" (a reasonable guess) or "airplane" (nonsense).

A teacher model's full output distribution is a soft label: instead of one correct answer, you get the teacher's confidence spread across many plausible continuations.

mat
52%
rug
23%
floor
14%
chair
6%
airplane
~0%

This is often called "dark knowledge"

The term (from Hinton, Vinyals & Dean's 2015 distillation paper) refers to exactly this: the relative ranking and confidence the teacher assigns to wrong answers. "Mat" beating "rug" by only 2x, while "airplane" is essentially zero, tells the student something about the shape of the problem that a single correct-answer label never could.

Concept

Temperature scaling

A model's raw softmax output is usually very peaked — often 90%+ confidence on the top token, with everything else squeezed into a tiny sliver of probability. At that sharpness, the dark knowledge from the section above is barely visible: "rug" might show as 2% instead of a more informative 23%.

Temperature (T) is a single number that turns up the "heat" on that distribution before comparing student and teacher, spreading the probability mass back out so the relative confidences among wrong answers become visible again. T=1 is the normal, unmodified softmax; T=2-4 is a common range for distillation, per this project's own plan.

Analogy: Squinting vs. really looking. A very confident softmax is like squinting at a photo until you only see the brightest point. Turning up temperature is like opening your eyes fully — the dim details (the runner-up answers) become visible again, without changing what's actually in the photo.
Standard softmax: p_i = exp(z_i) / Σ_j exp(z_j), where z are the raw logits. Temperature-scaled softmax divides every logit by T first: p_i = exp(z_i / T) / Σ_j exp(z_j / T). As T grows, the differences between logits shrink relative to T, so the resulting distribution flattens toward uniform. As T→0, it sharpens toward a one-hot vector on the single highest logit. Both the teacher's and student's outputs get divided by the same T before computing the distillation loss, so the comparison stays fair — this is also why the loss is typically scaled by T² when combined with a hard-label term, to keep gradient magnitudes comparable across different T values.
Concept

KL divergence

Once you have two probability distributions — the teacher's (temperature-scaled) output and the student's own — you need a number that measures how different they are, so you can push the student's distribution closer to the teacher's. That number is KL divergence (Kullback-Leibler divergence).

Analogy: Packing a suitcase using someone else's packing list. If your list assumes 3 shirts and 1 jacket, but you actually need 1 shirt and 3 jackets, you'll overpack shirts and scramble for jackets — the mismatch between the list you're using and what's actually needed costs you real, measurable inefficiency. KL divergence is that inefficiency, quantified: how many extra "bits" of surprise you pay by using the student's distribution as your guide when the teacher's is closer to the truth of what's actually likely.
For distributions P (teacher, treated as the reference) and Q (student): KL(P || Q) = Σ_i P(i) · log(P(i) / Q(i)). It's zero only when P and Q are identical, and grows the more Q assigns low probability to outcomes P considers likely. It is not symmetric — KL(P||Q) ≠ KL(Q||P) in general, which is why distillation conventionally uses the teacher as P and the student as Q: it penalizes the student for being confidently wrong about things the teacher was confident about, more than it penalizes the student for hedging on things the teacher was unsure of.

This is the piece that's yours to implement

Per this project's own CLAUDE.md, the actual distillation loss — hard cross-entropy, soft KL divergence with temperature, or the hybrid mix below — is a learning-objective piece, same boundary as train_step() and configure_optimizers in the phases before this one. This page explains the math; writing the loss function is the work that makes it actually understood.

Concept

The hybrid loss

In practice, distillation setups rarely use pure soft-label KL divergence alone — they mix it with the ordinary hard-label cross-entropy against the real next token, since the teacher's distribution is a helpful signal, not a perfect substitute for ground truth (the teacher can be wrong too).

This project's plan (`docs/plan.md`) frames it as three variants to actually compare, not assume:

1

Hard distillation

Plain cross-entropy against the teacher's single top-1 predicted token, instead of the real next token. Simple, but throws away all the soft-label information above.

2

Soft distillation

Pure KL divergence between student and temperature-scaled teacher distributions (T=2-4). Uses the full dark-knowledge signal, but never directly sees the real ground-truth token.

3

Hybrid

A weighted mix — this project's plan suggests 0.5 × KL + 0.5 × CE against the real token. Gets both signals at once; the weighting itself is a real hyperparameter to tune, not a fixed constant.

The plan is to compare all three on a small token budget (75-100M tokens) before committing to one for the full-scale run — cheap enough to actually test rather than guess.

The setup

The teacher model

Qwen 3.6 35B-A3B — a Mixture-of-Experts model, already downloaded on this machine (35GB GGUF, quantized). "A3B" means roughly 3B parameters are actually active per token, even though the model has 35B total — most of the weights are specialized "experts" that only activate for certain kinds of input.

Why that matters for a 16GB card

A dense 35B model at 4-bit quantization needs ~17.5GB just for weights — already over this card's 16.3GB. But an MoE only needs its active experts fast (on GPU); the rest can sit in system RAM and get swapped in on demand. This machine already has a config tuned exactly for that: CPU-offloaded experts, attention on GPU, using only ~3-4GB of VRAM. See sprint-plan.md for the current state of getting it actually running.

Q&A

Questions

Why not just train the small model from scratch on the same data? Why bother with a teacher at all?

Because raw text only ever tells you "this happened, this didn't" — hard labels, one correct token, zero information about which wrong answers were close. A well-trained teacher has already worked out the relative plausibility of every alternative, which is signal the raw corpus itself doesn't contain in an easily learnable form.

The honest empirical answer to "does that actually help enough to matter" is exactly what this phase's from-scratch baseline is for. If the distilled student doesn't beat it, that's a real, useful finding about this specific setup, not a reason to hide the baseline.

Why cache only the top-K (8192) logits instead of the full vocabulary?

Storage and signal-to-noise. The vocabulary here is 32K tokens, and the vast majority of them have essentially zero probability for any given context — storing all 32K logits per token position is mostly storing near-zero noise. The top 8192 captures effectively all of the meaningful probability mass while cutting storage roughly in quarter, and the tokens excluded contribute negligible KL-divergence signal anyway.

Does it matter that the teacher itself is a Mixture-of-Experts model?

Not for the distillation math — the student only ever sees the teacher's final output distribution, the same as it would for a dense teacher. MoE-vs-dense is entirely a teacher-side implementation detail; it changes how expensive the teacher is to run (see the VRAM card above), not what signal it produces for the student to learn from.

This machine reportedly gets ~80 tokens/sec from this teacher setup. Isn't that far too slow to generate logits for hundreds of millions of tokens?

That 80 tok/s number describes interactive chat generation — one token at a time, autoregressive, waiting on memory bandwidth for the CPU-offloaded MoE experts at every single step. That is not the operation Task 2 actually needs.

Generating teacher logits for distillation doesn't require generating any new text at all. The target tokens are already known (they're your existing training corpus) — this is a teacher-forced forward pass: feed in a whole batch of already-tokenized sequences at once and read off the logits at every position in a single pass, the same way a training step's forward pass works. That's a fundamentally different, typically much higher, throughput regime than token-by-token decode speed, because it batches over the sequence dimension instead of waiting on one token at a time.

Whether it's fast enough for a useful token budget is still a real open question — it just needs its own measurement (batched prefill throughput), not a reuse of the 80 tok/s decode number.
